## 首页四个视频的筛选与播放校验

用例：`test_four_home_videos_play_normally`。

### 第 1 轮：避免把照片选作视频

- 现场规则：封面右上角有摄像头图标才是视频；无标识是照片，不能默认首页前四张都是视频。
- 定位问题：iOS 会把卡片内容合并为一个可访问性按钮，不能始终从 XML 中拿到独立的摄像头标识。
- 修改：优先识别明确的摄像头标识；缺失独立节点时，使用真实设备截图提取的摄像头轮廓模板识别右上角。模板见 [home-camera-mask.png](../../velowind_appium/assets/home-camera-mask.png)。
- 选择方式：只打开判定为视频的卡片，按不同笔记累计四个；不足时继续浏览首页，避免重复同一篇。
- 检查：不接受黑屏、静止画面或错误提示作为正常播放。播放采样要求持续观察、画面变化及近期变化，保留选中卡片的截图。

可复用条件：XML 合并了视频图标，但卡片截图中有稳定可见的真实图标。不能把图标模板识别推广成任意媒体内容分类；遮挡、屏幕比例或图标变化后需要重新核对。

### 第 2 轮：播放错误文案误判与证据时序

- 用户反馈：失败附件中明明有视频画面，没有看到“视频暂时不可播放”。
- 分析：祖先容器可能汇总子节点文字，隐藏节点或短暂状态可能被当成当前错误；读取 XML 和截图之间状态也可能已经变化。
- 修改：错误判定聚焦明确状态标识或精确的叶子文本，并检查祖先可见性；捕获截图及前后 XML，确认错误在截图后仍存在。已消失的瞬态错误单独记录，继续验证实际播放。
- 不能采用的方法：仅在整份 XML 上搜索错误词，或因为截图中有一帧视频就断言持续播放正常。

### 第 3 轮：Allure 失败步骤归属

- 问题：跨视频累计失败时，报告可能把前一个视频的失败归到后一个视频步骤。
- 修改：在对应视频的 Allure 步骤内抛出可识别的播放失败，再在外层累计，保留正确的失败位置。
- 原则：错误应归到发生的那个视频；不能通过捕获异常把实际失败的步骤标成通过。

## 发布成功信号与目标卡片定位

涉及图片、相册视频、现场录制视频三个发布用例。

### 第 1 轮：识别 iOS 合并卡片标题

- 观察：我的笔记卡片常为 `post-home-feed-note-card-*` 按钮，标签结构类似“浏览量 标题 #话题 作者 点赞数”；没有独立标题 StaticText。
- 修改：`_ios_note_card_title` 从实际卡片标签解析标题，发布成功信号也识别这种卡片。
- 无效做法：只查精确标题 StaticText；把整页容器包含目标标题当成可点击目标。

### 第 2 轮：等待异步发布、避免旧笔记干扰

- 修改：发布后等待目标卡片插入列表；未出现时不向上滑离列表顶部，已在视口上方时向下滑找回。
- 修改：视频定位的发布等待与媒体内容校验等待分开，不把上传等待压缩为播放校验的短超时。
- 修改：小呆视频每轮使用不超过 20 字符的唯一标题后缀，降低打开旧同名视频的风险。
- 当时结果：发布用例通过，但这并未保证所有详情定位路径都核验了目标身份。
- 后续复发：图片用例仍误入另一篇视频。完整后续见 [2026-09-15 记录](2026-09-15-ios-publish-cleanup.md#问题一图片用例误入视频详情)，不能照搬本轮“标题匹配到就算定位完成”的实现。

## 功能遍历不能吞掉失败步骤

用例：`test_ios_feature_walkthrough`。

- 发现：一轮整套测试虽然显示通过，walkthrough 的可选入口异常处理却掩盖了内部失败步骤。
- 修改：租赁入口使用当前的 `wait_for_rental_store_page`；实际入口点击不放在会吞错的异常处理里；只有成功到达页面后才记录 visited；用 `finally` 返回，移除吞掉真实异常的处理。
- 验证要求：除 pytest 总结果外，还检查 Allure 的子步骤状态。

## 下次应优先参考的经验

1. 先核对选中的媒体类型和笔记身份，再判断播放器状态。
2. 合并标签需要解析实际卡片，不能点击包含所有笔记标题的祖先容器。
3. XML、截图和播放状态存在时间差，需要对照前后证据。
4. 分开检查总用例结果、子步骤状态和清理附件。
5. 长标题、换行、截断和详情定位的后续修复见下一篇；本篇的历史通过不能代表后续代码已完成验证。
